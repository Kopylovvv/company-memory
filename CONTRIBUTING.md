# Совместная работа

1. Выберите задачу с одним ответственным. Уточните результат и зависимости.
2. Создайте ветку от актуальной `main`: `feat/12-case-confirmation`, `fix/18-search`.
3. Делайте небольшие изменения в своей зоне; общие контракты согласуйте заранее.
4. Запустите подходящие проверки и опишите результат в pull request.
5. Другой участник просматривает изменения; после проверки объединяем в `main`.

На `main` должна оставаться запускаемая версия. Не храните несколько дней
изолированные части: каждый день проверяйте общую цепочку на общей версии.
Правило review — договорённость команды; branch protection пока не настроен.

## Коммиты

Сообщения на английском. Заголовок кратко описывает изменение, тело объясняет
причину, результат и проверку. Время и автор автоматически сохраняются Git.
Не добавляйте придуманные результаты тестов и не переписывайте чужую историю.

```text
feat(backend): persist case confirmations with source references

Store the confirming user and timestamp alongside each case so the UI can
separate reviewed experience from AI drafts. Reject repeated confirmations.

Validation: run the case API tests and confirm the flow through the mini app.
Refs: #12
```

Документация и задачи — на русском для команды; идентификаторы и коммиты — на
английском. В теле PR связывайте задачу через `Closes #N` только если она завершена.

## Журнал прогресса

Перед новой задачей прочитайте [журнал прогресса](docs/progress.md) и последние
сообщения Git. После существенного завершённого изменения добавьте запись в начало
журнала: результат, затронутые области, реальные проверки и следующий блокирующий
шаг. Не копируйте туда diff, промежуточные попытки и список каждого файла — детали
остаются в commit message, Issue и PR.

## Работа с AI-помощниками

Перед работой прочитайте корневой и ближайший к изменяемым файлам `AGENTS.md`,
журнал прогресса и последние сообщения Git.
Готовый шаблон запроса находится в [руководстве по работе с AI](docs/ai-assisted-development.md).
Перед генерацией определите вход, выход и способ проверки. Автор изменения должен
объяснить путь данных и продемонстрировать успешный сценарий и обработку ошибки.
Не просите AI изменять общий API, схему БД или зависимости без согласования.
Не передавайте секреты или реальные корпоративные данные в промпты.

## Готовность задачи

Код объединён, подходящие проверки прошли, инструкция обновлена, результат
показан в общем приложении. «Работает только у меня» не означает готовность.
