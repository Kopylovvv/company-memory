# Company Memory — «Компания, которая не забывает»

Чат-бот MAX команды **«барни со стволами»** для трека «Эффективный бизнес».
Бот превращает описание ремонта в черновик случая. Автор проверяет факты и
подтверждает его; коллеги затем находят похожий подтверждённый опыт.

**[Открыть работающего бота](https://max.ru/t58_hakaton_max_bot)** ·
[Публичный репозиторий](https://github.com/Kopylovvv/company-memory) ·
[Результаты проверки](docs/validation.md)

## Что реализовано

- Приём текстовых сообщений в MAX и сохранение исходника в PostgreSQL.
- Извлечение полей через YandexGPT: оборудование, симптом, причина, действие,
  результат и явно названный участник. Неизвестные факты остаются пустыми.
- Правка и подтверждение автором. AI сам случай не подтверждает.
- Поиск только подтверждённых случаев: симптом, действие, результат, сведения
  об источнике и участник, если он указан. Похожий случай — опыт коллег, не диагноз.
- Команды в меню MAX, работа с последним своим случаем без длинного ID,
  ввод аргументов следующим сообщением и отмена ожидания через `/cancel`.
- Защита от повторного сохранения одного события; исходный текст сохраняется
  и при недоступности AI.

MVP работает целиком в диалоге с ботом. React-страница предназначена для локальной
диагностики, **это не мини-приложение MAX**. История оборудования существует во
внутреннем API, но отдельной команды истории и открытия оригинала сообщения
в боте пока нет: в ответе поиска показываются тип источника и дата.

## Проверка работающего бота за несколько минут

Нужен обычный аккаунт MAX. Отдельные логин, пароль и API-ключи для этого сценария
не нужны; локально запускать проект не требуется. Используйте вымышленный номер
оборудования, чтобы отличить свой случай от предыдущих проверок.

1. Откройте бота и отправьте `/start` или `/help`. Ожидается инструкция.
2. Отправьте `/search Н-9428 течь сальника`. Если такой случай ещё не подтверждён,
   ожидается сообщение, что подтверждённых похожих случаев пока нет.
3. Отправьте обычный текст:

   ```text
   На насосе Н-9428 появилась течь сальника. Заменили прокладку, течь прекратилась
   ```

   Ожидается сохранённый черновик с оборудованием, симптомом, действием и
   результатом. Причина и участник не названы — бот не должен их придумывать.
   Перефразирование AI допустимо, факты должны совпадать с сообщением.
4. До подтверждения повторите поиск: **этот новый черновик** не должен появиться
   в результатах. Другие подтверждённые похожие случаи могут отображаться.
5. Отправьте `/edit результат течь прекратилась после замены прокладки`.
   Ожидается обновлённый черновик с новым результатом.
6. Отправьте `/confirm`. Ожидается подтверждение. Повторный `/confirm` должен
   сообщить, что этот случай уже подтверждён, без создания копии.
7. Отправьте `/search Н-9428 течь сальника`. Ожидается найденный случай с действием
   «заменили прокладку» и исправленным результатом. Источник — MAX и дата.
8. Выберите `/search` из подсказок или отправьте его без аргументов. Бот попросит
   запрос **следующим сообщением**. Отправьте `/cancel`: ожидание отменяется,
   следующее обычное сообщение снова воспринимается как описание нового ремонта.
9. Аналогично `/edit` без аргументов должен запросить поле и значение следующим
   сообщением. Его также можно отменить через `/cancel`.

Для проверки полностью пустого поиска используйте явно другую тему, например
`/search квантовый телепортатор не материализует груз`. Отсутствие точного ответа
на близкую ремонтную тему не всегда означает пустую выдачу: бот может найти
другие подтверждённые похожие случаи. Проверка с телефона и проверка кода —
разные уровни; выполненные проверки перечислены в [validation.md](docs/validation.md).

## Команды и правила диалога

| Команда | Что делает |
| --- | --- |
| `/start`, `/help` | Показывают инструкцию |
| `/search <описание>` | Ищет до трёх подтверждённых похожих случаев |
| `/search` | Просит запрос следующим сообщением |
| `/edit <поле> <значение>` | Исправляет последний свой случай, если он ещё черновик |
| `/edit` | Просит поле и значение следующим сообщением |
| `/confirm` | Подтверждает последний свой случай, если достаточно данных |
| `/cancel` | Отменяет ожидание ввода после `/search` или `/edit` |

Поля правки: `оборудование`, `симптом`, `причина`, `действие`, `результат`.
Для подтверждения нужны оборудование и хотя бы одно поле: симптом, действие
или результат. Остальные сведения могут оставаться пустыми. Команды без ID обращаются к **последнему своему случаю**:
повторный `/confirm` не выбирает вместо него более старый черновик. Чтобы выбрать
другой случай, сохранён совместимый синтаксис `/edit <ID> <поле> <значение>` и
`/confirm <ID>`; список ID через пользовательский интерфейс пока не реализован.

MAX может сразу отправить команду при нажатии на подсказку — это поддерживается.
Ожидание следующего сообщения длится пять минут и относится к конкретному
пользователю и чату. Другая команда переключает действие. После перезапуска бота
ожидание сбрасывается: отправьте команду заново. `/cancel` **не удаляет черновик
и не отменяет уже выполненное подтверждение**. Чужие случаи редактировать и
подтверждать нельзя; подтверждённый случай больше не редактируется.

## Архитектура

```text
MAX → Python-бот → YandexGPT (предлагает поля черновика)
                 → сервис случаев → PostgreSQL
MAX ← ответ бота ← правка / подтверждение / лексический поиск
```

Адаптер получает события через long polling, извлекает автора из события MAX и
вызывает общий сервис случаев напрямую. Поиск локальный: нормализация слов,
небольшой тезаурус, ранжирование и порог сходства; YandexGPT не генерирует ответ
поиска. Исходник, автор и время хранятся отдельно от изменяемых полей черновика;
сохраняются также автор и время подтверждения.

`backend` — FastAPI с внутренним API и миграциями; `bot` — отдельный процесс
из того же Python-образа; `db` — PostgreSQL 17; `frontend` — React/TypeScript
для диагностики. Рабочему боту не нужен входящий HTTP-порт. Caddy в production
конфигурации предусмотрен для HTTPS диагностического API, но не требуется
для диалога в MAX. [Подробная схема](docs/architecture.md).

## Воспроизводимый локальный запуск

### Подготовка

Нужны Git, Docker Engine и Docker Compose v2; Python и Node.js на хосте для
запуска контейнеров не нужны. Репозиторий публичный:

```sh
git clone https://github.com/Kopylovvv/company-memory.git
cd company-memory
cp .env.example .env
```

Для воспроизведения **сданной версии** используйте commit с первого слайда PDF
или исходники из сдаваемого архива. В Git: `git checkout <commit из PDF>`.
Заполните `.env` перед запуском бота:

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Локальная БД; пример содержит только демонстрационный пароль |
| `MAX_BOT_TOKEN` | Токен отдельного тестового MAX-бота |
| `LLM_API_KEY` | API-ключ сервисного аккаунта Yandex Cloud с доступом к Foundation Models |
| `YANDEX_FOLDER_ID` | ID каталога этого аккаунта Yandex Cloud |
| `YANDEX_GPT_MODEL` | Модель; если пусто, `yandexgpt/latest` |
| `LLM_TIMEOUT_SECONDS` | Таймаут AI-запроса, по умолчанию 20 секунд |

Рабочие секреты не публикуются в исходниках и PDF. Для самостоятельного запуска
нужны собственные тестовый бот и облачный доступ либо отдельно выданные командой
тестовые значения. Для проверки уже работающего бота они не нужны. **Не запускайте
второй poller с токеном рабочего стенда**: процессы будут делить события MAX.

В Docker-образ включён CA-бандл для MAX; `MAX_API_CA_BUNDLE` вручную задаётся
только при запуске Python вне Docker. `ALLOW_DEMO_IDENTITY` относится только
к отдельному локальному запуску API, стандартный Compose его не передаёт.
Подробнее о таком запуске — [development.md](docs/development.md).

### Одна команда запуска

Из корня после заполнения `.env`:

```sh
docker compose --profile bot up -d --build
```

Команда собирает образы, поднимает БД, применяет миграции и запускает API,
диагностическую страницу и бота. Первый запуск требует загрузки базовых образов
и зависимостей из интернета. Проверить состояние:

```sh
docker compose --profile bot ps
```

БД, backend и frontend должны стать `healthy`, бот — работать без завершения
процесса. Без токена можно запустить только локальную диагностику:
`docker compose up -d --build`. Это **не проверка общения в MAX**.

| Адрес / порт | Назначение |
| --- | --- |
| http://127.0.0.1:5173 | Диагностическая страница; ожидается «API доступен» |
| http://127.0.0.1:8000/api/health | Проверка процесса API; ожидается HTTP 200 |
| http://127.0.0.1:8000/docs | OpenAPI внутренних маршрутов |
| PostgreSQL 5432 | Только сеть Compose, наружу не опубликован |
| Бот | Входящего порта нет; исходящий HTTPS к MAX и YandexGPT |

API случаев по умолчанию возвращает `401` без проверенной личности.
Это ожидаемое поведение: продукт проверяется через MAX. Инструкция не предлагает
отдельный публичный HTTP API. Миграции выполняются автоматически до запуска
backend; бот ждёт готовности backend и использует ту же БД.

### Демо-данные

[Набор data/](data/README.md) содержит 20 синтетических сообщений и 19 запросов.
Оборудование и люди вымышлены, подключения к промышленному предприятию нет.
Для чистой локальной БД после старта Compose можно загрузить случаи:

```sh
docker compose run --rm -v "$PWD/data:/data:ro" backend .venv/bin/python -m app.ai.seed --data-dir /data
```

Повторная загрузка не создаёт копии. Черновики не участвуют в поиске,
предзагруженные случаи отмечены как демонстрационные. Сообщения, которые вы сами
пишете в MAX для теста, используйте также только синтетические. Основной сценарий
выше работает и без предзагрузки.

### Остановка, перезапуск, обновление

```sh
# Перезапустить процессы, сохранив данные
docker compose --profile bot restart
# Остановить и убрать контейнеры, сохранив том БД
docker compose --profile bot down
# Запустить снова; после изменения исходников пересобрать
docker compose --profile bot up -d --build
```

Подтверждённые случаи и черновики остаются в именованном томе PostgreSQL.
Команда `down -v` удалит этот том и данные — для обычной остановки она не нужна.
Production использует отдельные настройки: [infra/production.md](infra/production.md).

## Если что-то не работает

- **Бот не отвечает:** проверьте правильный аккаунт бота, его токен, работающий
  процесс и исходящий HTTPS; убедитесь, что с токеном запущен ровно один poller.
- **AI недоступен:** исходник остаётся в черновике, бот сообщает об ошибке.
  Проверьте ключ, каталог и облачные права. Можно заполнить поля вручную через
  `/edit оборудование Н-9428`, `/edit симптом течь сальника` и другие `/edit`,
  затем подтвердить. Повторного извлечения AI командой бота пока нет.
- **После нажатия `/search` нечего искать:** напишите запрос следующим сообщением;
  `/cancel` вернёт обычный ввод. Аналогично работает `/edit`.
- **Новый случай не находится:** сначала подтвердите его, проверьте оборудование
  и симптом, попробуйте более близкую формулировку. Поиск может пропустить
  перефразированный симптом; длинный ответ AI не доказывает качество поиска.
- **`/confirm` не проходит:** нужны оборудование и хотя бы симптом, действие или результат; исправлять можно
  только свой неподтверждённый случай. Подтверждённый повторно не изменяется.
- **HTTP API вернул `401`:** это нормально без проверенной личности MAX;
  локальная диагностика доступности — `/api/health`.

## Данные, доступ и ограничения

Исходные сообщения передаются в YandexGPT для извлечения полей. В демонстрации
используются только синтетические тексты. Автор сообщения не считается участником
ремонта автоматически. Пользовательское подтверждение означает проверку автором,
а не независимую экспертизу технической безопасности.

В текущем стенде **все пользователи бота видят подтверждённые случаи**. Разделения
по компаниям/группам и административного удаления через бота нет; промышленный
пилот требует политики доступа, хранения и удаления данных. Токены остаются на
сервере. В публичный репозиторий нельзя добавлять реальные рабочие сообщения,
персональные данные, `.env` или секреты.

Поиск лексический и зависит от формулировки. В проверочном наборе на 30.09.2026
ожидаемый случай попал в top-3 для **12 из 13** запросов с эталонным ответом;
есть один пропуск. Это маленький набор той же команды, а не доказательство
качества на реальных данных. Голос, фото, мини-приложение, интеграции с ТОиР и
автоматические рекомендации не реализованы. Экономия времени и простоев пока
не измерена; [план измерения](docs/demo.md) описывает следующий шаг.
