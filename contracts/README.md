# Data and API contract (Issue #2)

Контракт bot-only MVP принят тимлидом 22 сентября после реализации Андреем.
Источник истины по типам — Pydantic-модели в
`backend/app/cases/models.py`; они же формируют OpenAPI на `/docs` работающего
backend. JSON-файлы здесь — примеры для чтения и обсуждения, не заменяют
OpenAPI и должны оставаться с ним согласованными.

Реализация: HTTP-слой (`backend/app/api/cases.py`) не знает, какое хранилище
за ним стоит — оба варианта реализуют один интерфейс
(`app.cases.protocol.CaseServiceProtocol`) и не меняют формы запросов/ответов.
По умолчанию (в т.ч. в Docker Compose) используется PostgreSQL-репозиторий
(`backend/app/db/`, миграции в `backend/migrations/`, Issue #4). In-memory
сервис (`backend/app/cases/service.py`, Issue #2) остаётся только для быстрых
контрактных тестов без БД.

## Стабильные договорённости

- ID — строки; даты — ISO 8601 UTC (`received_at` без UTC-смещения отклоняется
  сервером).
- Источник сообщения (`source`) хранится отдельно от извлечённых полей и не
  перезаписывается при исправлении.
- Неизвестные факты — явный `null`, а не отсутствие поля и не выдумка модели.
- Неизвестное поле в запросе — ошибка `422`, а не молчаливое игнорирование
  (`extra: forbid` на всех схемах запроса).
- `cause` независим от `action`: сервер и AI не выводят причину автоматически
  из выполненного действия — только если причина явно названа в источнике.
- Автор сообщения (`source.author_id`) и участник ремонта (`participant`) —
  разные понятия; `participant` остаётся `null`, пока не назван явно.
- `draft` и `confirmed` — разные состояния `status`; подтверждение необратимо
  меняет статус и заполняет `confirmed_by`/`confirmed_at`, это делает только
  сервер, не клиент.
- Повторная доставка одного события MAX (`source.external_event_id`, иначе
  `source.id`) не создаёт новый случай — сервер возвращает существующий.

## Сущности

| Сущность | Поля | Примечание |
| --- | --- | --- |
| `Source` | `id`, `type` (`max_message`\|`manual`), `text`, `author_id`, `received_at`, `external_event_id` | Неизменяем после создания случая. |
| `Equipment` | `id`, `label` | `label` может быть `null`, если не выяснено. |
| `Participant` | `id`, `display_name` | Только явно указанный участник (для MVP этого достаточно). |
| `Case` | `id`, `status`, `source`, `equipment`, `symptom`, `cause`, `action`, `result`, `participant`, `confirmed_by`, `confirmed_at`, `created_at`, `updated_at`, `is_demo` | См. `case.example.json` (draft) и `case.confirmed.example.json` (confirmed). |

## Эндпоинты

Полные схемы и коды ошибок — на `/docs` (OpenAPI). Здесь — сводка.

| Действие | Метод и путь | Запрос | Успешный ответ | Ошибки |
| --- | --- | --- | --- | --- |
| Создание | `POST /api/cases` | `case.create.request.example.json` | `201` `case.example.json`; `200` то же тело при повторной доставке события | `401`, `422` валидация |
| Исправление | `PATCH /api/cases/{case_id}` | `case.correct.request.example.json` (частичное, отсутствующее поле — не трогать, явный `null` — очистить) | `200` обновлённый `Case` | `401`, `403` (не автор), `404`, `409` (случай уже подтверждён) |
| Подтверждение | `POST /api/cases/{case_id}/confirm` | `case.confirm.request.example.json` (те же необязательные поля, что и исправление) | `200` `case.confirmed.example.json` | `401`, `403` (не автор), `404`, `409` (уже подтверждён), `422` (не хватает оборудования и symptom/action/result) |
| Поиск | `GET /api/cases?q=&equipment_id=&limit=` | query-параметры, без тела | `200` `case.search.response.example.json` | `401`, `422` валидация параметров |
| История оборудования | `GET /api/equipment/{equipment_id}/history?limit=` | query-параметр `limit`, без тела | `200` `case.history.response.example.json` | `401`; нет истории → пустой `items`, не `404` |
| Ошибка (общая форма) | — | — | — | `error.example.json`: `{"error": {"code", "message"}}` |

Пагинация зарезервирована через `next_cursor` (сейчас всегда `null` — список
не превышает `limit`; курсорная реализация — при подключении реальной БД).
Поиск и история возвращают только `status == "confirmed"`.

## Идентичность и права (Issue #10)

Сервер сам решает, от чьего имени выполняется действие. В bot-only MVP
проверенный канал ровно один — события, которые бот забирает у MAX по своему
аутентифицированному соединению: `sender.user_id` там утверждает платформа,
поэтому `source.author_id` у случая — проверенная личность, а не поле клиента.

У HTTP API проверенной личности пока нет, поэтому **все маршруты `/api/cases*`
и `/api/equipment/*/history` по умолчанию отвечают `401 identity_not_verified`**.
`/api/health` остаётся открытым.

Для локальной разработки и ручных проверок можно включить заголовок
`X-Demo-User-Id`, выставив переменную окружения `ALLOW_DEMO_IDENTITY=true`.
Это **не** аутентификация: заголовок принимается как есть. В продакшене
переменная не выставляется, поэтому публичный запуск закрыт по умолчанию.

Минимальные права (для bot-only MVP; расширение — отдельной задачей):

| Действие | Кто может |
| --- | --- |
| Просмотр случая, поиск, история | любая принятая сервером личность |
| Исправление черновика | только автор исходного сообщения |
| Подтверждение черновика | только автор исходного сообщения |

Чужое исправление или подтверждение — `403 forbidden`, случай при этом не
меняется. `confirmed_by` сервер берёт из личности действующего пользователя;
клиент это поле не передаёт.

## Решения по ранее открытым вопросам

1. `Equipment{id, label}` достаточно для bot-only MVP. Отдельный справочник
   оборудования требует новой задачи и не блокирует текущую разработку.
2. `similarity_score` — число от `0` до `1` при поиске с `q` (Issue #8); большее
   значение означает более близкий результат. `match_explanation` — короткое
   фактическое объяснение совпавших полей, например
   `Совпадения — симптом: трясет; оборудование: Н-204`. Без `q` (просто список
   подтверждённых случаев) оба поля `null`. Похожих случаев нет — пустой `items`.
   Результат — подсказка из опыта, а не диагноз текущей поломки.
3. Подтверждение требует `equipment` и хотя бы одно из `symptom`, `action` или
   `result`. Это правило одинаково применяется in-memory и PostgreSQL-сервисами.
