# Архитектура и зоны ответственности

## Реализованный поток

```text
MAX Bot API → long polling → обработчик диалога
                            ├─ YandexGPT → проверенный по схеме AI-черновик
                            └─ общий сервис случаев → PostgreSQL
MAX Bot API ← ответ бота ← правка / подтверждение / локальный поиск
```

Бот вызывает `DbCaseService` напрямую, а не через HTTP API. Один Python-код
запускается двумя процессами: `bot` принимает события MAX, `backend` обслуживает
внутренний FastAPI и применяет Alembic-миграции. Оба используют одну БД.
React/TypeScript frontend — диагностическая страница, не мини-приложение MAX.
Микросервисов, очереди и векторной БД нет.

YandexGPT предлагает поля по исходному тексту. Структура проверяется Pydantic,
часть полей дополнительно проверяется на связь со словами исходника. Это снижает
риск выдуманных фактов, но не заменяет проверку человеком. При ошибке модели
создаётся пустой черновик с сохранённым источником и уведомлением.

Поиск — лексическое ранжирование подтверждённых случаев с нормализацией,
небольшим тезаурусом ремонтных слов и порогом сходства
(`backend/app/ai/search.py`). Внешняя модель не генерирует выдачу. Сейчас кандидаты
выбираются из подтверждённых случаев в памяти процесса поиска; для большой базы
потребуются измерение нагрузки и оптимизация. Выдача бота содержит до трёх случаев.

## Личность, состояние и источник

- Автор определяется из события MAX, полученного сервером с токеном бота.
- Исходное сообщение хранится отдельно от редактируемых полей случая.
- `draft` не участвует в поиске; `confirmed` появляется только после действия автора.
- Для подтверждения нужны оборудование и хотя бы симптом, действие или результат. Сохраняются автор и время
  подтверждения; редактирование подтверждённого случая запрещено.
- Автор сообщения и участник ремонта могут различаться; участник выводится только
  при наличии сведений о нём, а не угадывается по автору.
- Повторная доставка одного `mid` не создаёт второй случай.
- Последний свой случай определяется сервисом хранения; ожидание аргументов после
  `/search` и `/edit` живёт в памяти одного poller пять минут. `/cancel` отменяет
  ожидание, перезапуск его сбрасывает, сохранённый случай при этом остаётся в БД.
- Поиск текущего стенда доступен всем пользователям бота. Разделения по компаниям
  нет; это ограничение демонстрационного MVP.

## Внутренний API и запуск

`/api/health`, API создания/правки/подтверждения/поиска и история оборудования
реализованы; OpenAPI доступен на `/docs`. HTTP API случаев закрыт по умолчанию:
без проверенной личности возвращает `401`. Для отдельного локального процесса
разработчик может явно включить `ALLOW_DEMO_IDENTITY` и `X-Demo-User-Id`.
Обычный Compose и production этот режим не включают.

Long polling требует исходящий HTTPS к MAX и YandexGPT, входящий порт боту
не нужен. Caddy предусмотрен production-конфигурацией для диагностического
HTTPS API. PostgreSQL не публикуется наружу; данные сохраняются в Docker volume.
Токены и ключи читаются из окружения и не передаются frontend.

История оборудования есть во внутреннем API, но команды истории и открытия
оригинала сообщения в боте пока нет. Поиск показывает тип источника и дату.
