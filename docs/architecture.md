# Архитектура и зоны ответственности

## Поток данных

MAX → адаптер бота (Андрей) → AI-черновик (Макс) → PostgreSQL (Андрей).
Подтверждение пользователя → сохранённый случай → поиск (Макс) → API (Андрей)
→ ответ бота MAX (Андрей; сценарий и тексты — Егор). Запуск и интеграция —
Александр. React frontend остаётся заготовкой для необязательного мини-приложения.

Один backend на FastAPI с модулями. Отдельные микросервисы, очереди и векторная
БД не обязательны для MVP. Стратегию поиска и провайдера AI выбираем после
проверки правил и качества на небольшом наборе.

## Статус реализации

`/api/health`, стартовая frontend-страница и API случаев (создание,
исправление, подтверждение, поиск похожих случаев, история оборудования)
реализованы и сохраняются в PostgreSQL через Alembic-миграции
(`backend/migrations/`). Бот MAX принимает текстовые сообщения через long
polling и сохраняет их черновиками случаев (`backend/app/bot/`). Сценарий
диалога и AI-извлечение ещё не реализованы. Поиск (Issue #8) — лексическое
ранжирование подтверждённых случаев с тезаурусом ремонтной лексики и порогом
сходства, без внешнего AI (`backend/app/ai/search.py`). Личность пользователя берётся из проверенного события
MAX; HTTP API без проверенной личности отвечает `401`, а исправлять и
подтверждать черновик может только автор исходного сообщения
(см. `contracts/README.md`). Контракт bot-only MVP принят 22 сентября.

## Договорённости

- Источник сообщения хранится отдельно от извлечённых моделью полей.
- `draft` и `confirmed` — разные состояния. AI не может подтверждать случай.
- Подтверждение и изменение состояния разрешает сервер проверенному пользователю.
- Автор сообщения и участник ремонта — разные понятия; не приписывать опыт автору
  пересланного сообщения без основания. Первым MVP достаточно явно указанного участника.
- Случай найден по похожести, а не признан правильным решением текущей проблемы.
- В основном поиске только подтверждённые и доступные пользователю случаи.
- Повторное событие MAX не создаёт дубликат.
- Недоступность AI не уничтожает исходное сообщение; предусмотрены понятный статус
  ошибки и повторная обработка без дубликатов.
- Сервер проверяет данные запуска MAX; одного user_id из браузера недостаточно.
- Личность действующего пользователя приходит из проверенного канала MAX, а не из
  поля запроса; demo-заголовок доступен только при явно включённой переменной.
- Токены не попадают в браузер, репозиторий, логи и ответы API.

## Первый контракт

Черновик схемы и эндпоинтов — `contracts/README.md` и Pydantic-модели
`backend/app/cases/models.py`; они видны как OpenAPI на `/docs` работающего
backend. PostgreSQL используется по умолчанию; in-memory реализация остаётся
для быстрых контрактных тестов. Андрей владеет API и схемой хранения, Макс —
интерфейсами извлечения/поиска, Егор — потребителем HTTP API. Решения по
оборудованию, оценке похожести и минимальным данным подтверждения записаны в
`contracts/README.md`. Изменения согласовываем в задаче до переименования полей
в разных компонентах.
