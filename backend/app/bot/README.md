# MAX adapter — Андрей

Приём текстовых сообщений бота MAX и сохранение их как черновиков случаев
(Issue #5). Сценарий диалога, команды, кнопки и формулировки ответов — Issue
#16 (Егор); здесь только транспорт, отображение в контракт и подтверждение
приёма.

## Модули

- `settings.py` — настройки из окружения. Токен хранится в `SecretStr`, поэтому
  не печатается ни в логах, ни в traceback.
- `client.py` — HTTP-клиент MAX API с таймаутами. Токен уходит только в
  заголовке `Authorization`; тело ответа при ошибке не попадает в исключение.
- `models.py` — разбор payload MAX. Неизвестные поля игнорируются: это чужой
  API, он может добавлять поля (в отличие от нашего контракта, который
  неизвестные поля отклоняет).
- `handler.py` — `message_created` → `CaseCreateRequest` → хранилище случаев.
  Не зависит от транспорта, поэтому webhook сможет переиспользовать его как есть.
- `polling.py` — запуск long polling.

## Выбранный режим получения событий и его ограничения

Сейчас — **long polling** (`GET /updates`). Причина: webhook требует публичный
HTTPS с доверенным сертификатом, а публичный стенд ещё не поднят (#11), и
поднимать API наружу нельзя до проверки пользователя MAX (#10).

Ограничения, которые нужно помнить:

- Платформа документирует long polling как режим для разработки: ограничен по
  скорости и времени хранения событий; для продакшена рекомендуется webhook.
- Long polling и webhook взаимоисключающие: пока есть подписка на webhook,
  `/updates` работать не будет.
- Ограничение платформы — не более 30 запросов в секунду.
- Бот получает только события своих диалогов и чатов, куда его добавили;
  доступа к истории чатов и к старым сообщениям нет.

Переход на webhook: `POST /subscriptions` с публичным HTTPS-адресом. Хранение
случаев при этом не меняется — меняется только вызывающий код вокруг
`MaxUpdateHandler`.

## Сертификат: Russian Trusted Root CA

Сертификат `platform-api2.max.ru` выпущен «Russian Trusted Sub CA» (Минцифры).
Этого корня нет ни в системных хранилищах по умолчанию, ни в `certifi`, поэтому
обычный HTTPS-клиент падает с `CERTIFICATE_VERIFY_FAILED`.

Проверку сертификата **не отключаем**. Вместо этого укажите бандл, который
доверяет этому корню:

```sh
curl -o russian_trusted_root_ca.cer https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer
curl -o russian_trusted_sub_ca.cer  https://gu-st.ru/content/Other/doc/russian_trusted_sub_ca.cer
python -c "import certifi,pathlib,sys; print(pathlib.Path(certifi.where()).read_text())" > max-ca-bundle.pem
cat russian_trusted_root_ca.cer russian_trusted_sub_ca.cer >> max-ca-bundle.pem
export MAX_API_CA_BUNDLE=$PWD/max-ca-bundle.pem
```

На сервере альтернатива — установить корневой сертификат в системное хранилище
(`/usr/local/share/ca-certificates/` + `update-ca-certificates`); тогда
`MAX_API_CA_BUNDLE` не нужен. Решение о способе на проде за владельцем `infra/`.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `MAX_BOT_TOKEN` | Токен бота. Обязателен. Только окружение, никогда не в коде и не в Git. |
| `MAX_API_CA_BUNDLE` | Путь к CA-бандлу с Russian Trusted Root CA. Без него — ошибка TLS с понятным сообщением. |
| `MAX_API_BASE_URL` | Адрес API. По умолчанию `https://platform-api2.max.ru`. |

## Запуск

```sh
# из backend/, токен уже в окружении
uv run python -m app.bot.polling          # постоянный цикл
uv run python -m app.bot.polling --once   # один цикл, для проверки
```

Нужна поднятая PostgreSQL с применёнными миграциями: случаи сохраняются через
тот же репозиторий, что и API (`app.db.repository.DbCaseService`).

## Поведение

- Сохраняется только текст. Сообщение без текста получает короткий ответ, что
  поддерживается пока только текст, и случай не создаётся.
- `source.id` и `source.external_event_id` — `mid` сообщения MAX, поэтому
  повторная доставка не создаёт второй случай (уникальный индекс в БД), а
  отправитель не получает второй ответ.
- Сообщения от ботов и события других типов игнорируются: бот не отвечает сам себе.
- Извлечённые поля (`symptom`, `cause`, `action`, `result`, `participant`)
  остаются `null` — их заполняет AI-черновик (#6) и человек при подтверждении (#7).
- В логи попадают только идентификаторы (`mid`, id случая) — ни текст сообщения,
  ни токен.
