# Инструкции для AI-агентов

Этот файл действует для всего репозитория. Более близкий `AGENTS.md` внутри
папки дополняет эти правила для своей части проекта. Если инструкции расходятся,
следуйте более конкретному файлу, не нарушая продуктовые и безопасностные
ограничения из этого документа.

## Перед началом работы

1. Прочитайте `README.md`, `CONTRIBUTING.md`, `docs/progress.md`,
   `docs/product.md`, `docs/architecture.md`, `docs/roadmap.md` и
   `docs/development.md`.
2. Посмотрите последние изменения через `git log -5 --oneline` и при необходимости
   прочитайте тело относящегося к задаче коммита через `git show -s --format=fuller`.
3. Прочитайте выбранную GitHub Issue, её критерии приёмки и связанные задачи.
4. Проверьте фактическое состояние кода. Не выдавайте пункт плана или документации
   за уже реализованную функцию.
5. Кратко зафиксируйте вход, выход, зависимости и способ проверки изменения.
6. Работайте только в границах выбранной Issue. Если нужен общий контракт, схема
   БД или новая зависимость, сначала отразите решение в Issue или pull request.

`docs/progress.md` — краткая карта уже выполненного, а Git и Issues — источник
точных деталей. Не перечитывайте весь код для восстановления истории, но сверяйте
с кодом факты, которые важны для текущего изменения.

## Неизменяемые правила продукта

- Исходное сообщение хранится отдельно от извлечённой структуры.
- Результат AI всегда является черновиком. Подтверждение делает человек.
- Неизвестные факты остаются пустыми; модель не должна их придумывать.
- Автор сообщения и участник решения могут быть разными людьми.
- Поиск использует только подтверждённые и доступные пользователю случаи.
- Похожий случай — подсказка из опыта, а не гарантированный диагноз.
- Повторная доставка одного события не должна создавать дубликаты.
- Ошибка AI не должна приводить к потере исходного сообщения.
- Данные запуска MAX проверяются на backend; токены и секреты остаются на сервере.

## Технические границы MVP

- Сохраняйте единый FastAPI backend и React frontend, описанные в архитектуре.
- Не добавляйте микросервисы, очередь, векторную БД или нового AI-провайдера без
  отдельной задачи и понятной причины для MVP.
- Не меняйте публичный API, модель данных или версии общих зависимостей скрытно.
- Используйте синтетические данные. Не добавляйте токены, персональные данные,
  реальные корпоративные сообщения и содержимое `.env`.
- Делайте небольшие, проверяемые изменения. Не переписывайте соседний код без
  необходимости для выбранной задачи.

## Проверка и сдача изменения

Запускайте только относящиеся к изменению проверки, описанные в
`docs/development.md`. Для общего контракта проверяйте и backend, и frontend.
Обязательно проверьте успешный сценарий и ожидаемую ошибку.

Перед завершением:

- сравните результат с критериями Issue;
- добавьте в начало `docs/progress.md` краткую запись, если задача меняет поведение,
  архитектуру, контракт, инфраструктуру или порядок работы команды;
- обновите документацию и примеры контракта, если поведение изменилось;
- перечислите выполненные проверки без придуманных результатов;
- убедитесь, что в diff нет секретов и случайных сгенерированных файлов;
- используйте английский подробный commit message и свяжите PR с Issue.

Не считайте задачу готовой, если изменение нельзя запустить по инструкции или
показать в общей цепочке приложения.
