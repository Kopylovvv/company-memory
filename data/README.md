# Demo and evaluation data — Макс

**Все данные здесь синтетические** (Issue #3): сообщения, оборудование и люди
выдуманы. Реальные документы и исходные датасеты предыдущего проекта не переносим
без проверки прав и правил хакатона. Формат случая — `../contracts/case.example.json`.

## Файлы

`demo_messages.json` — 20 рабочих сообщений, 7 единиц оборудования, 5 участников.
Для каждого сообщения указаны:

- `expected` — эталонное извлечение для оценки AI-черновика (#6). `null` значит,
  что факт в тексте не назван, и модель должна оставить поле пустым. Причина
  не выводится из действия: «заменили уплотнения» не означает названную причину.
- `load` — как сообщение попадает в демо-базу: `confirmed` (подтверждённый опыт,
  по нему ищет поиск), `draft` (черновик, поиск не должен его возвращать) или
  `none` (только для оценки извлечения либо живое сообщение демо).
- `tags` — что проверяет сообщение: `incomplete`, `negation`, `unknown_equipment`,
  `injection`, `same_symptom_diff_cause`, `cause_not_stated`, `author_not_participant`,
  `equipment_id_variant`, `not_a_repair`, `draft_only`, `live_demo` и другие.

`search_queries.json` — 19 проверочных запросов для поиска (#8):

- `expected_source_ids` — попадание: любой из этих источников в первых трёх
  результатах. Пустой список — нет эталонного ответа; допустим пустой ответ либо только
  связанные случаи из `acceptable_source_ids`.
- `acceptable_source_ids` — связанные случаи (то же оборудование, соседняя тема):
  показать их не ошибка, но и не попадание.
- `phase` — `seed` для демо-базы; `after_live` — после подтверждения живого
  сообщения `demo-src-17`. Запросы `q-18` и `q-19` одинаковые: до демо ответ
  пустой, после — находится новый случай (главный момент показа).
- `measurement_task` — пять задач для мини-измерения из `docs/demo.md`.

Ожидаемые результаты ссылаются на `source.id`, а не на ID случая: ID случая
назначает сервер при создании, и он меняется между запусками.

## Что покрыто

- Одинаковые симптомы с разными причинами: вибрация Н-204/Н-205 (муфта, подшипник,
  дисбаланс колеса), перегрев К-101 (радиатор, уровень масла), проскальзывание
  ленты КЛ-3 (натяжение не помогло, футеровка барабана).
- Неполные сообщения, отрицания («не помогло», «муфта в порядке»), неизвестное
  оборудование, другое написание ID (`КЛ3`), сообщение не о ремонте.
- Попытка инструкции внутри сообщения (`demo-src-13`) — эталон не меняется.
- Автор сообщения и участник ремонта — разные люди (`demo-src-16`).
- Запросы без ответа и запросы, которым соответствует только черновик.

Набор намеренно небольшой и не подогнан под один показательный запрос; метрики
на нём — проверка работоспособности, а не доказательство качества.

## Проверка и загрузка

Согласованность файлов и загрузка через правила случаев проверяются тестом
(из `backend/`):

```sh
uv run pytest tests/test_demo_dataset.py
```

Загрузка демо-базы идёт через те же правила создания и подтверждения, что у бота
и API. Все случаи помечаются `is_demo`. Повторный запуск дубликатов не создаёт.
При запущенном `docker compose up` (миграции применяет backend) из корня:

```sh
docker compose run --rm -v "$PWD/data:/data:ro" backend .venv/bin/python -m app.ai.seed --data-dir /data
```

Вне Docker из `backend/` при доступной БД из `POSTGRES_*`:

```sh
uv run python -m app.ai.seed
```

Папку с данными можно указать через `--data-dir` или переменную `DEMO_DATA_DIR`.
